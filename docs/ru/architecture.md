# Архитектура и Дизайн

> **Модуль:** `docs/ru/architecture.md`
> **Контекст:** Общесистемные архитектурные решения, организация модулей и потоки данных.

## 1. Высокоуровневый обзор

**Aura Launcher** (ранее SCOpenLauncher) реализует модульную, реактивную архитектуру, разработанную для отделения пользовательского интерфейса от бизнес-логики. Проект следует прагматичной реализации **Чистой Архитектуры** (Clean Architecture), адаптированной для Desktop Compose.

Система разделена на четыре отдельных слоя:

1.  **Слой представления (`client-ui`)**:
    * **Ответственность:** Рендеринг UI, обработка ввода пользователя и наблюдение за состоянием.
    * **Технологии:** Compose Multiplatform (Desktop), Koin (Consumption).
    * **Ограничение:** Не содержит *никакой* бизнес-логики. Делегирует все действия Контроллерам.

2.  **Слой оркестрации (`client-ui/logic`)**:
    * **Ответственность:** Мост между UI и Domain слоями. Управляет реактивным состоянием (`LaunchState`), обрабатывает корутины для UI-действий и оркестрирует множественные сервисы (например, «Логин затем Запуск»).
    * **Ключевой компонент:** `LauncherController`.

3.  **Слой инфраструктуры/сервисов (`client-launcher`)**:
    * **Ответственность:** Реализует основную бизнес-логику, определённую в `client-core`. Работает с файловой системой, сетью, хешированием и управлением процессами ОС.
    * **Технологии:** Ktor Client (движок OkHttp), `java.lang.ProcessBuilder`.

4.  **Слой домена и контрактов (`client-core`)**:
    * **Ответственность:** Определяет *что* (Интерфейсы) и *данные* (DTO), но не *как*.
    * **Ограничение:** Чистый Kotlin. Никаких зависимостей от фреймворков (Ktor, Compose и т.д.).

## 2. Структура модулей

Проект использует многомодульную структуру Gradle для обеспечения разделения ответственности.

| Модуль | Пространство имен | Роль и Зависимости |
| :--- | :--- | :--- |
| **`client-config`** | `hivens.config` | **Статическая конфигурация.**<br>Содержит константы времени сборки (`AppConfig`), такие как Версия, API URL и размеры окна по умолчанию.<br>*Зависимости: Нет* |
| **`client-core`** | `hivens.core` | **Контракты и Данные.**<br>Определяет "API" приложения. Включает интерфейсы (`ILauncherService`, `IAuthService`) и неизменяемые модели данных (`SessionData`, `ServerProfile`).<br>*Зависимости: `client-config`* |
| **`client-launcher`** | `hivens.launcher` | **Реализация.**<br>"Тяжеловес". Реализует интерфейсы из `core`. Содержит DI модули (`appModule`, `networkModule`), которые связывают эти реализации.<br>*Зависимости: `client-core`* |
| **`client-ui`** | `hivens.ui` | **Представление.**<br>Точка входа (`Main.kt`). Определяет логику UI, экраны и компоненты. Инициализирует граф Koin.<br>*Зависимости: `client-launcher`* |

## 3. Внедрение зависимостей (Koin)

Приложение строит граф объектов во время выполнения, используя **Koin**. Граф строго иерархичен.

### Инициализация

DI-контейнер запускается в `hivens.ui.Main.kt` непосредственно перед созданием окна приложения.

```kotlin
startKoin {
    modules(networkModule, appModule, uiModule)
}
```

### Определения модулей

1. **`networkModule`** (Источник: `client-launcher/di/Modules.kt`):
* Предоставляет синглтоны `OkHttpClient` (Движок) и `HttpClient` (Ktor).
* Настраивает SOCKS прокси, таймауты и JSON сериализацию.


2. **`appModule`** (Источник: `client-launcher/di/Modules.kt`):
* Связывает Core Интерфейсы с Launcher Реализациями.
* Пример: `single<ILauncherService> { LauncherService(...) }`.
* Пример: `single<ISettingsService> { SettingsService(...) }`.


3. **`uiModule`** (Источник: `client-ui/Main.kt`):
* Предоставляет UI-специфичные контроллеры.
* Пример: `singleOf(::LauncherController)`.
* *Примечание:* Определен локально в `Main.kt`, чтобы `client-launcher` не зависел от логики UI.



## 4. Поток данных: Последовательность запуска

Взаимодействие между слоями во время запуска игры иллюстрирует архитектуру:

1. **Событие UI:** Пользователь нажимает "Играть" в `DashboardScreen`.
2. **Действие контроллера:** `DashboardScreen` вызывает `controller.launch(session, server)`.
3. **Обновление состояния:** `LauncherController` обновляет `LaunchState` на `Preparing`.
4. **Оркестрация сервисов:** `LauncherController` вызывает `launcherService.launchClient(...)`.
* *Внутри сервиса:* Проверка Java → Проверка файлов → Сборка аргументов → Запуск процесса.


5. **Передача процесса:** Сервис возвращает `java.lang.Process`.
6. **Мониторинг:** `LauncherController` следит за `process.waitFor()` в IO-потоке и обновляет `LaunchState` на `GameRunning`.

## 5. Ключевые паттерны проектирования

### 5.1 Разделение интерфейсов

Модуль `client-ui` никогда не создает экземпляры классов логики напрямую. Он запрашивает зависимости через интерфейсы, определенные в `client-core`.

* *Преимущество:* Мы можем заменить всю реализацию `LauncherService` (например, для тестов или другого движка) без изменения единой строчки UI-кода.

### 5.2 Реактивное состояние (MVI-lite)

UI наблюдает за единственным источником правды о статусе запуска.

* **Состояние:** `LauncherController.state` (Тип: `StateFlow<LaunchState>`).
* **События:** UI вызывает функции контроллера, который внутри себя мутирует состояние. UI *никогда* не изменяет состояние напрямую.

### 5.3 Движок тем

Темизация управляется кастомным `SeasonTheme` enum в `client-core`, отвязанным от Compose.

* **Логика:** `SeasonTheme.getCurrentSeasonalTheme()` вычисляет тему на основе системной даты.
* **Рендеринг:** `CelestiaTheme` и `CelestiaBackground` в `client-ui` используют этот enum для отрисовки визуальных эффектов (Снег, Светлячки и т.д.).
