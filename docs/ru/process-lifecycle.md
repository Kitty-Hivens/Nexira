# Жизненный цикл процесса и Пайплайн запуска

> **Модуль:** `docs/ru/process-lifecycle.md`
> **Контекст:** Детальный разбор последовательности запуска игры, верификации файлов и оркестрации процесса.

## 1. Пайплайн запуска

Процесс запуска представляет собой линейный конвейер (pipeline), управляемый сервисом `LauncherService`. Он преобразует запрос пользователя в запущенный процесс ОС. Пайплайн спроектирован по принципу **fail-fast**: если какой-либо шаг не удается (например, отсутствует Java, неверный хеш), выполнение немедленно прерывается с конкретным исключением.

### Диаграмма последовательности (Абстрактная)

1.  **Подготовка (Preparation):** Проверка/Установка Java Runtime -> Обеспечение структуры директорий.
2.  **Верификация (Verification):** Получение манифеста -> Хеширование и проверка целостности -> Загрузка отсутствующих/поврежденных файлов.
3.  **Сборка (Construction):** Разрешение нативных библиотек -> Сборка Classpath -> Формирование аргументов JVM.
4.  **Исполнение (Execution):** Порождение процесса -> Подключение слушателей логов.

---

## 2. Шаг 1: Подготовка окружения

Прежде чем трогать игровые файлы, лаунчер убеждается, что хост-окружение готово. Эта логика находится в `EnvironmentPreparer` и `JavaManagerService`.

### 2.1 Разрешение Java Runtime

**Сервис:** `JavaManagerService`

Лаунчер не полагается на общесистемную переменную `JAVA_HOME`. Он строго требует наличия конкретной версии Java для процесса игры (в настоящее время поддерживаются **Java 8, 17 или 21** в зависимости от версии Minecraft).

1.  **Проверка:** Проверяет, существует ли валидная JRE по внутреннему пути (например, `updates/jre`).
2.  **Валидация:** Запускает `java -version`, чтобы убедиться, что бинарный файл исполняемый и соответствует требуемой архитектуре.
3.  **Условие отказа:** Если Java отсутствует или повреждена, выбрасывается `LaunchException` (Авто-загрузка Java запланирована, но пока выполняется вручную или через пре-пакинг).

### 2.2 Структура директорий

**Сервис:** `ClientFileHelper`

Обеспечивает существование «песочницы»:

* `client/`: Корневая папка игры (рабочая директория).
* `client/bin/`: Нативные библиотеки и JAR-файлы ядра.
* `client/assets/`: Ассеты Minecraft (объекты, индексы).
* `client/mods/`: Контент загрузчика модов.

## 3. Шаг 2: Верификация целостности

**Сервис:** `FileIntegrityService`

Aura использует надежную систему хеширования, чтобы гарантировать полное соответствие клиента состоянию сервера.

### 3.1 Манифест (`FileManifest`)

Верификация управляется DTO `FileManifest`, полученным от бэкенда.

* **Структура:** Содержит список объектов `FileData`.
* **Свойства:** `path` (относительный), `hash` (SHA-1/SHA-256), `size` (байты), `required` (boolean).

### 3.2 Алгоритм хеширования

Сервис итерируется по каждому файлу, определенному в манифесте:

1.  **Существует?** Если файл отсутствует -> Пометить как **MISSING**.
2.  **Совпадение размера?** Если размер отличается от манифеста -> Пометить как **INVALID**.
3.  **Совпадение хеша?** Вычисляет SHA-1 (или SHA-256) хеш локального файла.
    * Если `localHash != remoteHash` -> Пометить как **INVALID**.
4.  **Валиден:** Если все проверки пройдены -> Пометить как **VALID**.

**Оптимизация:** Лаунчер выполняет эти проверки параллельно (используя Coroutines) для ускорения запуска больших модпаков.

### 3.3 Исправление (Загрузка)

**Сервис:** `FileDownloadService`

Любой файл, помеченный как **MISSING** или **INVALID**, добавляется в очередь загрузки.

* Файлы загружаются через `Ktor`/`OkHttp`.
* Используются временные файлы (`.part`) для предотвращения повреждения при прерывании загрузки.
* После загрузки хеш проверяется повторно.

## 4. Шаг 3: Сборка команды

**Сервис:** `GameCommandBuilder`

Когда файлы в безопасности, лаунчер собирает массивную строку командной строки для запуска JVM.

### 4.1 Группы аргументов

Аргументы собираются в определенном порядке:

1.  **Исполняемый файл:** Путь к бинарнику `java`.
2.  **JVM Флаги (Память):**
    * `-Xmx{allocated}M`: Размер кучи (из Настроек).
    * `-Xms512M`: Начальный размер кучи.
3.  **JVM Флаги (Система):**
    * `-Djava.library.path=...`: Путь к нативным библиотекам (LWJGL).
    * `-Dfile.encoding=UTF-8`: Принудительная кодировка.
    * OS-специфичные флаги (например, настройки иконки в доке macOS).
4.  **Classpath (`-cp`):**
    * **Сервис:** `ClasspathProvider`.
    * Сканирует `client/bin` и `client/libraries` для сборки строки classpath. Разделитель зависит от ОС (`:` для Unix, `;` для Windows).
5.  **Main Class:** например, `net.minecraft.client.main.Main`.
6.  **Игровые аргументы:**
    * `--username`: Логин игрока.
    * `--uuid`: UUID игрока.
    * `--accessToken`: Токен сессии.
    * `--version`: Версия индекса ассетов.
    * `--gameDir`: Путь к `client/`.
    * `--assetsDir`: Путь к `client/assets/`.

## 5. Шаг 4: Исполнение процесса и Мониторинг

**Сервис:** `LauncherService` и `ProcessLogHandler`

### 5.1 Порождение процесса

Собранный список команд передается в `ProcessBuilder`.

* **Рабочая директория:** Устанавливается в корень клиента (критично для модов/конфигов).
* **Окружение:** Наследует системный PATH, но переопределяет специфичные переменные при необходимости.

```kotlin
val process = processBuilder.start()
```

### 5.2 Обработка вывода логов

Процесс Minecraft пишет логи в `STDOUT`, а ошибки в `STDERR`.

* **Проблема:** Если лаунчер будет ждать процесс, не вычитывая эти потоки, буфер переполнится, вызвав зависание игры (Deadlock).
* **Решение:** `LauncherService` запускает две фоновые корутины сразу после старта:
1. Читает `process.inputStream` -> Перенаправляет в Консоль Лаунчера (INFO).
2. Читает `process.errorStream` -> Перенаправляет в Консоль Лаунчера (ERROR).



### 5.3 Обработка выхода

`LauncherController` (в UI слое) ожидает завершения процесса используя `process.waitFor()`.

* **Код выхода 0:** Чистое завершение.
* **Код выхода != 0:** Краш. Контроллер оставляет консоль открытой, чтобы пользователь мог видеть лог ошибки.
